## D-01 运行时平台：自建 Node + SQLite + React，而非飞书妙搭 / 多维表格

**背景**：课程要求网站「云端运行、国内普通网络可访问、无需安装软件、无需逐人申请权限、不索取个人模型密钥」；原方案优先考虑飞书妙搭 + 飞书多维表格。

**候选方案**
| 方案 | 优点 | 障碍 |
|---|---|---|
| A. 飞书妙搭 + 多维表格 | 小组无需写代码即可维护内容 | 匿名公开访问与服务端密钥托管能力**本次无法核实**；复杂关系查询与全文检索实现成本高 |
| B. 自建 Node + SQLite + React | 完全可控、可离线运行、可导出、无平台锁定 | 需要自己实现维护界面与部署 |
| C. 第三方 BaaS（Supabase 等） | 免运维数据库 | 需境外账号与密钥；国内访问稳定性未知；数据出境合规风险 |

**决定**：采用 B。

**依据**
1. 实际核实结果：抓取 `feishu.cn/product/miaoda`、`feishu.cn/miaoda`、开放平台妙搭文档路径均返回 404 或仅空壳标题；多维表格 API 文档页正文由前端异步渲染，抓取只得到标题（记录于来源 S-21、S-22、S-23）。因此「妙搭能否匿名公开访问 + 服务端安全调用第三方模型 API」记为**无法核实**。
2. 方案 5.1 明确要求「不得将未经验证的平台能力当作前提」。
3. `node:sqlite` 为 Node.js 官方内置模块（S-27），本地实测 Node v24.21.0 可用，零原生编译依赖、零额外服务、零费用。

**取舍与被放弃项**
- 放弃「小组无需写代码即可维护内容」这一便利 → 以管理端 Web 界面 + CSV/JSON 导出补偿（`npm run export` 可直接把数据搬进多维表格）。
- 放弃平台的托管运维 → 以 Dockerfile、docker-compose、systemd 说明与备份脚本补偿（见 `docs/DEPLOY.md`、`docs/OPERATIONS.md`）。
- **诚实边界**：本决定不等于「妙搭不满足要求」。本项目没有能力证明它不满足，只是无法核实它满足，故结论限定为「不作为架构前提」。

**重新权衡的条件**：若有账号权限的成员实测确认妙搭支持匿名公开访问与服务端密钥托管，可把内容层迁回妙搭/多维表格（导出脚本已就绪），本站保留为检索与 AI 管线层。

## D-02 存储：SQLite 单文件，而非向量数据库或托管数据库

**背景**：需要存节点、关系、来源、更新记录、反馈、候选内容六类实体，并支持全文检索与跨表关联。

**候选方案**：A. SQLite（node:sqlite）；B. PostgreSQL/MySQL 托管服务；C. 向量数据库（Qdrant/Pinecone 等）+ 关系库双写；D. 纯 JSON 文件。

**决定**：采用 A，九张表：`nodes` `relations` `sources` `update_log` `feedback` `candidate_content` `eval_items` `eval_runs` `ai_usage`。

**依据**
1. 方案 8.3 要求「数据可备份、可导出，尽量避免被单一平台锁定」→ 单文件 + JSON/CSV 导出最彻底。
2. 方案 8.1 要求普通访问者无需登录、无需密钥 → SQLite 不需要数据库账号体系。
3. 语料规模小（142 节点 / 238 关系 / 44 来源），SQLite 完全够用。
4. 关系模型天然支持外键与唯一约束，可用 CHECK 约束把内容治理规则落到数据库层（见 D-08）。

**取舍与被放弃项**
- 放弃高并发写入能力 → 本项目写入只发生在管理端与反馈提交，量级极小。
- 放弃向量检索 → 见 D-04。
- 放弃多实例水平扩展 → 若未来需要，可用 `npm run export` 迁移到 PostgreSQL（schema 为标准 SQL，迁移脚本成本低）。

**重新权衡的条件**：并发写入显著增加，或语料扩展到十万级节点，或需要多实例部署。

## D-03 检索：自建轻量检索，而非 LangChain / LlamaIndex

**背景**：RAG 管线需要「把课程资料变成可检索资产」。

**候选方案**：A. LangChain；B. LlamaIndex；C. 自建（BM25 + IDF + 同义词 + passage 级打分 + 一跳图扩展）。

**决定**：采用 C。

**依据**
1. 管线单一：只有一条固定 RAG 链路，框架的抽象层收益有限。
2. 课堂演示与互评需要**可逐行解释**的实现；自建代码约 400 行，框架内部行为难以在 8 分钟内讲清。
3. 减少依赖树 → 降低版本风险与安装失败概率（本次交付环境无网络代理保证）。
4. 检索可解释性对课程要求「区分事实与推断」有直接价值：每次检索返回命中字段与得分明细，前端展示「为什么命中」。

**取舍与被放弃项**
- 放弃框架提供的现成 Retriever / 多模型路由 / 记忆管理 → 本项目不需要。
- 放弃社区生态与长期维护 → 以自建代码的可读性与测试覆盖（79 个单元测试）补偿。

**重新权衡的条件**：需要多模型路由、多种检索器并存、复杂工具编排，或团队规模扩大到多人协作开发。

## D-04 检索算法：BM25 + IDF + passage 级打分 + 图扩展，而非向量检索

**背景**：这是本项目调优投入最大的一处，全部结论来自实测数据。

**候选方案**：A. 嵌入向量检索（需嵌入模型 + 向量库）；B. 关键词检索（BM25）；C. 混合召回。

**决定**：采用 B，并做了四轮实测驱动的改进。

**实测驱动的改进过程（真实记录，可复现）**

| 轮次 | 发现的问题 | 修正 | 效果（14 题平均节点召回率） |
|---|---|---|---|
| 1 | 单字高频词（「课」「程」）命中几乎所有节点，淹没有效词 | 引入 IDF，对文档频率高的词降权 | 64.3% → 73.2% |
| 2 | 关系文档的 title 由两端节点标题拼接，命中大量查询词，在混合榜中挤占节点名额 | 按类型分别取 top-K（节点/关系/来源各自成池）；关系 title 不再参与索引 | EV-08 节点召回 33% → 67% |
| 3 | `relation_type` 只有 1–2 token，BM25 长度归一化使短字段得分暴涨：查「GLM-4.7-Flash 价格」时所有 `定价` 关系排在名字里就含该实体的模型节点之前 | 关系不设 title 索引字段；BM25 文档长度设 25% avgLen 地板；对「实体型词元」（如 `glm-4.7-flash`）在标题中逐字命中给予强加成 | 该查询下模型节点 rank 7 → rank 2 |
| 4 | `details` 是多条要点拼接的长文本，长度归一化用全文长度惩罚其中一条高度相关的要点：查「访问权限与密钥要求」时正文明确列出这些要求的节点排第 19 位 | passage-level BM25：`details` 按条分别打分取最高分（与本项目 D-C-CHUNK 节点主张的「以节点为分块单位」一致） | 该节点 rank 19 → rank 10 |
| 5 | 查询用词与语料用词不一致：用户问「访问权限」，语料写「无需逐人申请权限」 | 扩充同义词表（访问权限↔访问要求↔公开访问↔无需逐人申请权限；密钥↔凭据↔API Key 等**真实等价词**，非关键词堆砌） | 64.3% → **69.1%**，且「至少命中一个相关节点」从 13/14 提升到 **14/14** |

**为什么不选 A（向量检索）**
1. 语料规模小（数百条可检索单元），向量检索的召回优势不明显。
2. 少一个外部服务与一份密钥 → 降低维护成本与安全风险。
3. 可解释性：关键词检索能说出命中了哪个词、哪个字段、得多少分，这对课堂演示与同学自查更重要。

**已知代价（诚实标注）**：对完全换了说法的同义问题召回仍有限。已记录在 `D-C-EMB` 与 `D-R-RETRIEVAL` 节点的 `limit` 字段，以及评测报告的局限性章节。

**重新权衡的条件**：语料扩展到全书/多课程规模，或需要跨语言检索 → 应引入嵌入检索做混合召回（检索层已设计为可复用函数，可直接注册为一个 tool）。

## D-05 AI 路线：固定 RAG 管线，而非智能体式多步检索

**背景**：方案要求「必须完成一项真正与地图数据集成的 AI 功能」。

**候选方案**：A. 固定 RAG 管线（服务端检索 → 注入上下文 → 生成 → 引用校验）；B. 智能体式（ReAct / FLARE / Self-RAG，模型自主决定检索时机与次数）。

**决定**：采用 A。

**依据（多目标取舍）**
| 目标 | A 固定管线 | B 智能体 |
|---|---|---|
| 准确率 | 课程问答以单跳/双跳为主，够用 | 多跳问题更好 |
| 响应时间 | 实测 4–18 秒（单轮） | 按步数线性增长，十几秒到数十秒 |
| 成本 | 一次调用，可预估 | 按步数增长，难预估 |
| 可复现性 | 高（管线确定） | 低（步数与路径随输入变化） |
| 课堂演示 | 8 分钟内可稳定复现 | 难以稳定复现 |

硬约束是**响应时间 + 成本可控 + 可复现**，因此选 A。

**保留的演进接口**：检索层被设计为独立可复用函数（`server/lib/retrieval.mjs` 的 `search` / `buildContext`），若未来接入工具调用，可直接注册为一个 tool 而不必重写管线。

**依据来源**：ReAct（S-04，ICLR 2023）、FLARE（S-13，EMNLP 2023）、Self-RAG（S-09）均已核实并作为生态与领域节点记录，未实现的原因写在节点 `limit` 字段中。

## D-06 模型渠道：主 GLM-4.7-Flash（免费档）+ 备 deepseek-flash，双渠道自动降级

**背景**：方案 5.3 要求「至少配置一个主模型和一个可切换备用模型；若外部 API 无法配置，必须提供基于已审核地图内容的非生成式搜索/解释降级能力」。

**决定**
- 主渠道：智谱 GLM-4.7-Flash（官方定价页标注输入/输出均「免费」，200K 上下文，核查日期 2026-11-01，S-15）。
- 备用渠道：DeepSeek deepseek-flash（1M 上下文，输入空闲 1 元/百万 tokens，S-17）。
- 三级降级：主渠道失败 → 备用渠道 → 全部失败则**非生成式检索直出**（不调用任何模型，直接用检索命中的节点、关系与来源组织答案）。

**依据**
1. 免费档使课堂演示与 14 题评测的反复运行几乎不产生费用，这是学生项目可行的前提。
2. 两家均提供 OpenAI 兼容形态（S-17、S-18），切换成本在配置层而非代码层。
3. 非生成式降级保证「即使外部 API 完全不可用，网站核心功能仍完整可用」——这是方案 5.3 的硬要求，本项目已实测验证（无密钥时 E2E 全绿）。

**诚实标注**：本次交付未取得 DeepSeek 官方密钥，备用渠道的**代码路径完整可用**（切换 BASE URL 与 Key 即可），但对 DeepSeek 官方端点的真实调用**未验证**；实际评测通过本机已配置的 OpenAI 兼容网关完成，网关暴露的模型名为 `glm-*` 系列。相关节点（`D-T-DSAPI`）证据状态标为「部分核实」。

**实测发现（已修正的真实缺陷）**：调用 `glm-4.7-flash` 时 `max_tokens=1400` 导致 `reasoning_tokens=1394`、`content` 为空——思考型渠道会先消耗推理额度。
- 错误做法（曾实现，已移除）：`content` 为空时回退展示 `reasoning_content`，结果用户看到的是模型内部推演草稿而非答案。
- 正确做法（现实现）：把 `max_tokens` 提到 3200（上限 4000），识别 `finish_reason=length` 或「有 reasoning 无 content」为**截断**，自动提高预算重试一次；仍失败则如实上报 `status=truncated`，**绝不用思考过程冒充答案**。

**重新权衡的条件**：免费档策略调整（快变量，需每周复核定价页）；或任务复杂度上升到需要旗舰档推理能力。

## D-07 上下文构造：限制片段数 + top 片段置首尾，而非塞满窗口

**依据**：Lost in the Middle（S-08，TACL 2023）实证关键信息位于长上下文中间时使用效果显著下降，性能呈 U 形。

**决定**：检索结果按分数降序取前 K（默认 5），提示中把 top-1 片段置于资料区首、top-2 置于尾；不为提高召回而塞满窗口。

**取舍**：牺牲「尽可能多的资料」换取「模型能有效使用资料」+ 更低的 token 成本。这是「一篇论文直接改变一段代码」的实例，已记录在认知地图 `C-REV-CTX`。

## D-08 内容治理：把规则落到数据库约束，而非只写在文档里

**决定**：用 CHECK 约束、外键、唯一索引与写入校验把治理规则变成**技术上不可违反**：

| 规则 | 实现位置 |
|---|---|
| 证据状态只能四级 | `nodes.evidence_status` / `relations.evidence_status` CHECK 约束 |
| `knowledge_status` 不得由 AI 猜测 | CHECK 约束限定四个值；种子数据全部为「未评估」；单元测试断言无一被填入 |
| `taught_in` 必须说明覆盖程度 | 写入校验：`relation_type==='taught_in' && !coverage` → 拒绝 |
| 推断关系必须附推理链 | 写入校验：`evidence_status==='推断' && !reasoning_chain` → 拒绝 |
| 正式节点必须有来源 | 写入校验：`source_ids` 为空且无 `evidence_note` 说明 → 拒绝（此校验为实测发现缺口后补上，见下） |
| 关系类型受控 | 写入校验 + `npm run lint:data` 双重检查 |
| 来源被引用时不可删除 | `deleteSource` 先查引用 |
| 同一对节点同类型关系不重复 | 唯一索引 `(source_node_id, target_node_id, relation_type)` |
| 候选内容不直接进正式地图 | `candidate_content` 独立表 + `is_candidate` 标志 + 审核状态机 |

**实测发现并修正的缺口**：初版 `validateNode` 未校验 `source_ids` 非空，导致管理端能写入自家 `lint` 判为 error 的数据（单元测试捕获后修复）。这说明「校验规则」与「一致性检查」必须同源，否则会出现自己违反自己规则的情况。

## D-09 拒答判定：词汇重叠率作为硬闸门，而非只看相似度分数

**背景**：必须实现「无命中或证据不足时明确说明，不得自由编造地图内容」。

**踩过的坑（三轮，全部实测）**
1. 第一版：置信度 = top 得分 / 25。结果「量子引力与弦理论」得 0.69、「如何烤蛋糕」得 0.82 —— 越界问题置信度比领域内问题还高，拒答机制形同虚设。
2. 第二版：改为「命中的查询词占比」。结果短查询（3 个词）只要碰巧命中一个常见字就是 1.0，同样失效。
3. 第三版（现实现）：**IDF 加权的词汇重叠率** —— 分母包含「语料中不存在的查询词」（按长度加权），因此完全越界的查询自然得到低重叠率。

**实测分离效果**（阈值 0.62）：
- 领域内 8 个问题：重叠率 0.74 – 0.92（均值 0.84）
- 领域外 6 个问题：重叠率 0.25 – 0.59（均值 0.42）
- **可完全分离**，无交叉。

**双层闸门设计**
- 第一层（scope gate）：重叠率 < 0.62 → `out_of_scope`，**不调用模型**（省成本，且避免模型用通用知识强行作答），前端显示「知识边界雾化」提示 + 下一步入口。
- 第二层（内容层拒答）：课程范围内但资料未覆盖的问题（如具体课名）重叠率仍高（≥0.73），不会被第一层拦截，而是交由模型基于「缺口节点」做内容层拒答，说明缺什么、去哪补。

**为什么必须两层**：EV-11「大二有哪些必修课」与「怎么做红烧肉」性质不同——前者在领域内但资料缺失，后者完全越界。单层闸门无法区分，会把前者也拦掉，丢失「说明缺口 + 给出补录入口」的价值。

**同源一致性要求**：搜索接口使用同一阈值（`SEARCH_OVERLAP_FLOOR`），否则会出现「搜索说有结果、AI 说越界」的自相矛盾（实测触发过，已统一）。

## D-10 会议类别：一律不标注 CCF A/B 类

**背景**：课程要求生态地图关注「CCF A 类会议」；方案要求「不得凭印象标注会议类别」。

**实际情况**：访问 `www.ccf.org.cn/Academic_Evaluation/By_category/`、`/AI/`、`/CGAndMT/` 三个路径均返回站点 WAF 挑战页（响应体含 `CF_APP_WAF`），未能取得目录正文（记录于 S-41）。

**决定**：所有论文一律**不标注** CCF 类别，该字段记为「待核实」；只保留可核实的会议名。

**替代核实路径（双源交叉）**
1. arXiv 摘要页 `Comments` 字段（一手）；
2. Semantic Scholar Graph API 的 `venue` 字段（独立聚合源）。

结果：14 篇论文中 **6 篇双源一致**（RAG/NeurIPS 2020、ReAct/ICLR、MT-Bench/NeurIPS 2023 D&B、RARR/ACL 2023、FLARE/EMNLP 2023、Lost in the Middle/TACL），6 篇单源印证标为「部分核实」，2 篇为持续更新的 arXiv 预印本综述（HELM、RAG Survey）标为「预印本」。

**取舍**：生态地图少了「A 类会议」这一显性标签，换来全部会议信息可追溯。这一决策过程本身被记录为认知地图的真实案例 `C-CASE-CCF` 与认识修正 `C-REV-EVIDENCE`。

## D-12 前端：React 19 + Vite + Tailwind v4 + Zustand，X-Ray 用原生 SVG

**依据**：方案 §三 指定技术栈为 React 18+ / TypeScript / Vite / Tailwind / Zustand / SVG。实际安装到的版本为 React 19.3.1、Vite 8.3.5、Tailwind 4.3.3、Zustand 5.0.16（均为 2026-11-01 的 npm latest）。

**Tailwind v4 要点**：通过 `@tailwindcss/vite` 插件接入，CSS 中 `@import "tailwindcss"`，主题用 `@theme` 定义而非 `tailwind.config.js`（S-28）。本项目据此把「庄重典雅」设计语言落成 CSS-first 语义 Token：墨色 / 宣纸 / 朱砂 / 翡翠 / 琥珀 / 科技蓝，明暗双主题共用同一套语义变量。

**Vite 8 适配（实测踩坑）**：Vite 8 底层为 Rolldown，`manualChunks` 必须是**函数**而非对象；配置文件需用 `import.meta.dirname` 而非 `__dirname`。两处均已在 `web/vite.config.ts` 修正。

**X-Ray 用原生 SVG 而非 React Flow**：
- 方案 §三 提到「SVG / React Flow」二选一。选原生 SVG 的原因：本项目地图按板块分组渲染卡片列表，节点位置由文档流决定而非固定坐标，React Flow 的受控布局模型反而需要额外适配层；原生 SVG + `getBoundingClientRect` 测量可直接在任意布局上连线，且零额外依赖。
- **实测踩坑（重要）**：初版直接在长列表卡片之间连线，67 个节点的地图页中选中节点的关联节点常在视口之外，端点过滤后**连线数为 0**，核心亮点功能等于没生效。修正方案：新增「X-Ray 关联星群」面板（`XRayConstellation.tsx`），把当前节点与其关联节点渲染成一块紧凑区域，连线锚点统一为星群内的 `data-xray-id` 元素，因此不受滚动位置影响。修正后 E2E 实测画出 20 条 path。

## D-13 移动端：抽屉式多维标签流，而非缩放桌面布局

**依据**：方案 §四「屏幕宽度 < 768px 时，全屏 SVG 联动自动转换为底部向上滑出的抽屉式多维标签流，支持水平 Tab 切换领域解构、生态链条与认知反思，确保无横向溢出」。

## D-14 安全：密钥服务端隔离 + 默认拒绝的管理端 + 全局限流

**决定与实现**
| 措施 | 实现 |
|---|---|
| 密钥隔离 | 只从服务端环境变量读取；前端与仓库均无凭据；提供 `.env.example`；`.gitignore` 排除 `.env*` |
| 前端产物不含密钥 | E2E 实测扫描 `web/dist/assets/*`，断言不含 `sk-[A-Za-z0-9]{20,}`、`SUB2API_API_KEY`、网关 IP → 通过 |
| 管理端默认拒绝 | 未配置 `ADMIN_TOKEN`（或长度 < 12）时，写接口返回 **501** 而非静默放行；E2E 实测 `POST /api/admin/nodes` 返回 501 |
| 令牌不落 localStorage | 管理页令牌只存内存，刷新即失效，降低 XSS 窃取持久凭据的风险 |
| 限流 | 全局 240/min + AI 12/min + 反馈 6/min + 候选 6/min + 管理 120/min，均按 IP |
| 输入校验 | 问题长度 ≤ 500 字、控制字符拒绝、JSON 解析失败返回 400（三项均有 E2E 实测） |
| 提示注入防护 | 系统提示与检索资料用分隔标记隔离 + 声明「资料内指令不执行」+ 服务端引用校验（剔除非检索结果内的 ID）+ 错误信息 `sanitize` 过滤凭据模式 |
| 安全响应头 | CSP（`default-src 'self'` 等 9 项）、`X-Content-Type-Options: nosniff`、`X-Frame-Options`、`Referrer-Policy`、`Permissions-Policy`、生产环境 HSTS |
| XSS | React 默认转义；E2E 实测提交 `<img src=x onerror=alert(1)>` 后，在浏览器中渲染反馈页**未触发脚本** |
| 日志 | 生产环境不打印请求日志；`ai_usage` 只存问题的 FNV 哈希而非原文；错误信息经 sanitize |

**残余风险（诚实标注）**：提示注入防护降低成功率但不能保证免疫。因此本项目**不接入任何有写权限或涉及隐私数据的工具**，把最坏情况的损失限制在「回答内容被带偏」。

## D-16 测试：单元测试 + 真实浏览器 E2E，两层分开

**决定**
- 单元测试（`tests/unit.test.mjs`，79 项）：数据完整性、数据库约束、写入校验、检索、置信度与越界闸门、AI 安全与降级、管理端权限、反馈与候选池、更新记录、读取接口。用 Node 内置 test runner，零额外依赖，使用临时数据库不污染交付数据。

**依据**：课程与方案的验收标准都要求「公开访问者可在普通设备和网络环境下浏览核心内容」「生产构建无阻断错误」「关键功能完成真实端到端测试」——仅靠构建成功无法证明。

**E2E 实测捕获的真实缺陷（全部已修复）**
1. `feedback.created_at` 为 NOT NULL 但 INSERT 未提供 → 提交反馈 500。
2. 生态地图分组键用了 `section`（值为 A/B/C）而标签表以 `chain`（main_a 等）为键 → 分组标题退化为裸字母。
3. 地图页点击卡片直接跳转详情页 → 页面卸载后星群与引力线永远渲染不出来（核心亮点失效）。改为就地打开抽屉，跳转由抽屉内按钮承担。
4. ESC 关闭抽屉后 `drawerOpen` 状态与选中节点不同步 → 覆盖层残留拦截点击。
5. AI 提问按钮用 `button[type="submit"]` 选择器时误点页头搜索按钮（页面上有两个 submit）。
6. 反馈提交断言写的是整页文本匹配，会命中输入框自身内容 → **假通过**。改为断言成功提示元素 + 输入框已清空 + 列表出现该条记录。

8. ESM 中 `import { loadEnv }` 后再调用会晚于其他模块的模块级常量求值 → 改为 env 模块导入即生效。
9. Playwright 1.62.1 期望 Chromium build 1234，本地缓存为 1248；且完整版 chromium 在 `--remote-debugging-pipe` 下 `spawn UNKNOWN` → 改为按优先级尝试 headless_shell / chromium / 系统 Chrome。

**测试隔离**：E2E 与单元测试各用独立数据库（`data/test-e2e.sqlite` / 临时目录），避免测试产生的反馈、用量记录污染交付数据；另提供 `npm run reset-db` 一键恢复干净种子状态。

## D-17 托管平台：Cloudflare Workers + D1（已部署），并以 Pages 版解决国内可达性

**背景**：课程要求「云端运行、不依赖个人电脑开机、国内普通网络可访问」。隧道方案（serveo/localhost.run）已实测可用但为临时性质（serveo 免费隧道约 10 分钟过期），不满足长期要求。账号所有者在 Edge 登录 Cloudflare 并完成 Wrangler 设备授权后，Agent 得以完成真实云部署。

**候选方案**
| 方案 | 优点 | 障碍 |
|---|---|---|
| A. Cloudflare Workers + D1 | 边缘托管、免运维、免费额度充足、D1 与 SQLite 同构 | `workers.dev` 在中国大陆被 DNS 污染（实测） |
| B. Cloudflare Pages（`_worker.js` + 静态） | 同 A 的代码与数据，但 `pages.dev` 未被污染、国内可达 | 需 legacy Pages 部署，Wrangler 设 `--force` 护栏 |
| C. VPS + systemd | 完全可控、可用自有域名 | 需服务器与备案，成本与运维最高 |
| D. 隧道（serveo/localhost.run） | 零账号、立即可用 | 临时地址、依赖本机开机，不满足课程长期要求 |

**决定**：采用 A 作为已部署的主托管（全球可达、长期稳定）；以 B 作为国内可达地址的候选（待用户授权 `--force`）；C/D 保留为备选。

**依据（实测，2026-11-01）**
1. 原始 DNS 报文直查五种解析器：`*.workers.dev` 在 AliDNS/DNSPod/Google/本机均返回伪造 IP（104.244.43.167、154.83.15.45、31.13.94.10 等非 Cloudflare 段）；仅加密 DoH（1.1.1.1）返回真实 Cloudflare IP（172.67.130.72 / 104.21.3.58）。
2. 同样的解析器查 `*.pages.dev` 返回真实 Cloudflare 段（104.16–198.41），未被污染。
3. Worker 部署后公网冒烟 18/18 通过；D1 与本地 SQLite 数据完全一致（同源种子、同 schema）。

**实现要点**
- 检索内核抽为 `shared/retrieval-core.mjs`，Node 版与 Worker 版**共用同一实现**（BM25 + IDF + passage 级 + 同义词 + 相关性下限），避免两套算法漂移；Node 侧仅保留数据库访问与图扩展包装。
- 重构后以「召回率回归测试」验证行为一致：14 题平均节点召回率保持 69.1%（重构曾一度降到 65.5%，定位为图扩展的相关性下限应用顺序与系数漂移，已按原始顺序复原）。
- Worker 内实现 SPA 深链接回落（静态 404 且 `Accept: text/html` 时回 `index.html`），不依赖平台配置。
- 密钥（LLM_API_KEY / LLM_BASE_URL / LLM_MODEL / ADMIN_TOKEN）存为 Worker secret；`/api/ai/status` 不返回 baseUrl。

**取舍与被放弃项**
- Worker 生成模式调用当前兼容网关返回 Cloudflare 1003（网关封禁 Cloudflare 出口 ASN）→ Worker 版 AI 运行在检索直出降级模式。换官方端点 secret 即恢复（一行命令，见 EXTERNAL-BLOCKERS）。
- D1 与本地库为单向同步（本地 → D1）；D1 新增数据不自动回流。若以 Worker 为唯一生产库，应停止本地写或建立回流导出。

**重新权衡的条件**：账号获得自有域名 zone → 绑定 Custom Domain 彻底解决 DNS 污染；或用户授权 `--force` → 立即获得 `*.pages.dev` 国内可达地址。
